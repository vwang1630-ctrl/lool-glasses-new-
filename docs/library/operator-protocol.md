## 1. Current Truth Protocol(压五核心之上的地基)

**九个字:一张表、两道门、默认假。**
核心命题:**"存在"≠"当前有效"。Fresh ≠ True,True ≠ Current——两道门都过,才是 Current Usable Truth。**
立法理由(原话):*"过期真事实比 AI 胡编更危险,因为它看起来完全像真的。"*——四次实锤:PayPal 双状态并存(manual L841 vs L1115)、$35k 假信号存活 5 天、8 笔测试 wire 被当"真钱"挂 P0 三周、74 展示基线过期 11 天仍被引用。

### 1.1 事实宪法表(一张表)

| 事实 | 权威源(现任) | 门一:新鲜度策略 | 门二:真伪 | 可解锁动作 | Fallback |
|---|---|---|---|---|---|
| PayPal 状态 | 当前配置+T1 验证 | 事件驱动(变更即更新,无 TTL) | 配置本身即真伪 | 支付 | 人工核验(级3) |
| Wire 通道 | 当前配置+银行 | 事件驱动 | 收入默认 T0,站主盖章升 T1 | 支付 | 人工核验(级3) |
| 订单/收入 | DB | 实时读取(不缓存) | **默认 T0(测试),站主显式盖章才 T1** | Revenue 台账 | 站主确认 |
| 咨询 | consult_events DB | 实时 | 过 t1 自测甄别(T0 剔除) | 销售动作 | — |
| 客户阶段 | 当前客户记录 | 事件驱动 | T0/T1 分层 | 销售 | 人工核验 |
| GSC/流量 | gsc-export.json | TTL 7d(拉取即新) | 实测无真伪问题,但禁当"现值"引用过期数 | SEO/流量判断 | 下次拉取 |
| GA4/行为 | GA4 | TTL 7d | 同上 | 流量判断 | 下次拉取 |
| 部署状态 | deploy-smoke | 事件+异常探测 | — | 系统动作 | 人工检查 |
| 画像/口径 | framework-lock(总阀门) | 事件驱动(版本号) | canonical 词表=真伪基准 | 内容生产 | validate 闸门 |

### 1.2 两道门

- **门一 Freshness(它几岁)**:有验证时间且未超适用策略 → FRESH;无验证时间或已超 → **STALE**。
- **门二 Authenticity(它是谁的)**:T0=自测/站主/系统行为 → 永不进真实商业学习;T1=真实客户一手且经规定确认 → 才进成交学习。
- **$35k 打穿门二(新鲜但假),74 展示打穿门一(真实但过期)**——两例各验一道门,缺一不可。

### 1.3 默认假(Default Stale)——第零条

**任何缺少可验证时间戳的事实,默认 STALE;不得因其存在于手册、台账、数据库或记忆中而推定为当前有效。**宁标 STALE,不造假 FRESH——假新鲜比诚实的过期毒十倍。

### 1.4 事实分两类(防"每日重验"假工作)

- **配置类**(支付开关/部署/画像):只在有人改它时变 → **事件驱动**,变更即更新+记录谁改的+时间;不设 TTL。真正要盯的是源头异常(token 死——GSC token 前科在案)。
- **测量类**(GSC/GA4/流量/咨询数):世界自己在变,数据自然腐烂 → **TTL 合理**,过期即 STALE。

### 1.5 状态四值与查询纪律

- **FRESH / STALE / UNKNOWN / CONFLICT** 四态。STALE≠废弃,=「当前未知,需重新验证」。
- **CONFLICT 只发生在两个有现任权威的来源之间**(Manual=沙盒 vs Live=开 **不是** CONFLICT——Manual 无出庭资格)。Payment config=live 但 T1 支付测试失败 = CONFLICT。
- **STALE/UNKNOWN/CONFLICT 状态下,依赖该事实的动作一律冻结**(熔断+失败关闭原则)。
- **查询纪律**:①"现在是什么状态"只准从活数据/带时间戳记录回答,禁止从叙事文档回答;②手册/台账只回答"当时为什么";③Mixed 问题拆成两半分别走两条路。

### 1.6 验收测试(四条,从实锤直接导出)

1. **过期测试**:给 verified_at=9-21 的 74 展示,问当前基线 → 必须拒绝当现值;
2. **历史测试**:问"9-21 当时 GSC 多少" → 可答 74/0(历史问题);
3. **资格测试**:Manual=沙盒 vs 配置=live → 答 live 并注明来源+验证时间;
4. **自过期测试**:状态文件自身超期 → 答"当前无法确认",不得答旧值。

## 2. Priority Engine(调度规则)

| 级 | 定义 | 备注 |
|---|---|---|
| **P0-AI** | 钱/客户/交易风险中 AI 可直接执行 | 当日最高 |
| **P0-Human** | 只你能动的:银行核验、支付切换、真实订单盖章 | AI 备料+提醒,**永不 Closed** |
| **P1** | 制造成交机会(Signal Pump) | **P0 为空时强制落 here,禁漂 P3** |
| **P2** | 长期资产 | |
| **P3** | 优化效率(CRO/关键词/页面) | **traffic L0/L1 整级冻结** |

### 3.5 可靠性条款(SRE-lite,2026-10-02 站主批)

三条 SLO(月度例会过目,连续越线才动手,防过度焦虑):
1. **月可用率 ≥99%**(watchdog 每 5 分钟实测为准)
2. **deploy-smoke 通过率 100%**(任一失败=事故,当次复盘)
3. **PDP 首字节 <2s**(实测基线 198-3478ms,余量大)

部署安全:
- **部署前必跑** `node scripts/deploy-rollback.cjs backup`(当前版→last-good)
- 部署坏 → `node scripts/deploy-rollback.cjs rollback` + 重启 80——最坏情况从分钟级压到秒级
- **重启前喊一声**“重启,约 10 秒不可用”(2026-10-02 站主撞黑窗后立)
- 明确不做(锁死复杂度):多区域/K8s/on-call/微服务——0 真实用户阶段的最优 SRE=复杂度不涨

## 5. Strategic Memory(扩展 judgment-log.md,不建平行日志)

```json
{ "judgment":"", "evidence_level":"T1-T4", "source":"",
  "before":"", "after":"", "confidence":"", "next_test":"",
  "reuse_count":0, "last_reused":"", "effectiveness":"",
  "decision_status":"hypothesis|testing|validated|failed|archived" }
```

- 入库=显著性四门槛(改变未来动作/有证据来源/可复用/有结果反馈),缺一留 judgment-log 普通日志;
- `testing` 到 `next_test` 期自动进 Brief ⑤;挂钩 UNFALSIFIED 保质期规则(超期未证伪=FAIL);
- `reuse_count`=0 且超期 → 提议 archived(进沉淀池,不销毁);
- **禁"提升X%"**:必须绝对计数("7 天咨询 3→5,样本不足,趋势观察"),样本够格升百分比由 signal_state 说了算。

## 7. 数据水管规则(2026-10-02 站主三问沉淀)

1. **新水入管,先判断定**:**补充**(新异议/新观察)→ 兑旧水升版本+记配方(改了哪几条/依据什么);**推翻**(新事实打脸旧事实)→ 旧水归档降级,**当前龙头只出一种水**。怕的不是新旧结合,是结合了不记版本(PayPal 双状态教训)。
2. **新水必须流遍全身**:"新增一个事实"不算完成,"所有连着它的地方都换新"才算——改源头→顺管 sweep 画像/Pin/blog/FAQ/口径引用点→报"**全站 N 处已同步**"(N 须站主可抽查)。
3. **废水三桶**:当前管(FRESH+真)可饮;**沉淀池**(archived/failed/旧版本)不流但留档可查——多数"没用"的水归宿在这;**下水道**(真销毁)仅限密钥/隐私/纯垃圾副本——标准:删了不丢知识、只降风险。
4. 行业对应:TTL+事件失效(缓存)、SCD Type 2(版本留档)、MDM(总阀门)、银行对账(默认验真)。
